# Implementation plan: Godot Rapier Physics for Redot

- Original/current program priority: 7 / 7
- Planning baseline date: 2026-08-10
- Planning approval: closed by explicit owner instruction on 2026-08-11
- Implementation disposition: local Rapier2D `0.35.2-redot.1` implementation and automated Windows/Linux candidate matrix complete; external promotion gates remain open

## Implementation completion snapshot

As of 2026-08-12, all local automated Rapier2D milestones in this plan pass: full upstream 2D parity, six editor/debug/release native artifacts, Windows/Linux unit and regression coverage, cross-platform lockstep replay, frozen performance guardrails, exact-feature legal/SBOM output, deterministic packaging, selected/default clean installs, and official-template debug/release export launches. The exact unpublished archive is SHA-256 `af8ec56c054981c3c699f166efd91ae1685fda18a87d67762603e609d984b258`.

Stable promotion remains blocked on retained downstream-project confirmation or the defined owner waiver, public pinned CI for the source revision, and explicit authorization for the version tag and release channels. Source publication to the public fork is separately authorized. Rapier3D remains outside the implementation scope unless its Jolt added-capability gate passes.

## Assumptions and boundaries

- Redot 26.2 stable and its recorded single-precision API JSON are authoritative.
- Each plugin release certifies one exact Redot engine release/commit and API identity. The first planned release targets Redot 26.2/API 4.5.2; another Redot version requires a separately tagged and fully validated downstream release rather than inheriting compatibility.
- `dominicbytes/redot-rust` commit `18ad5c538c452b8640420366794354e3ed48f205` is the shared compatibility prerequisite, not proof that Rapier works.
- Use owner-pinned Godot Rapier Physics `v0.35.2` with its committed `rapier2d 0.35.1` and `rapier3d 0.35.1` lock for this release line. Do not float to `main`, a prerelease, or a later stable; evaluate later upstream versions in a future planned update.
- After the first release, monitor every official upstream stable plugin and Rapier crate release and begin a recorded evaluation promptly. Promise no fixed publication deadline: retain the current pin until the newer source passes every applicable compatibility and release gate, and publish the evaluated/current-pin status plus any blocking reason.
- Provide routine maintenance only for the newest published Redot-specific plugin line. Older exact-Redot releases remain downloadable and documented but receive no routine fixes, dependency updates, or feature backports.
- Open routine plugin update cycles with planned stable Redot releases, expected roughly quarterly. Review repository pull requests and issues between cycles, record their disposition and target Redot cycle when applicable, and queue accepted routine work without promising an immediate release or response-time SLA.
- Permit a narrowly scoped out-of-cycle patch on the current supported line only for a confirmed security defect, data-loss defect, or release-blocking crash. The exception changes timing, not quality: full applicable release gates remain mandatory, and features or routine dependency upgrades stay queued for the next Redot cycle.
- Rapier remains opt-in. Untouched projects must keep their current Redot physics backend.
- Maintain one source repository with two independently installable addon slots. Rapier2D is the first release; Rapier3D ships only if it adds a material, testable user-facing capability that the pinned Redot Jolt backend does not provide.
- Preserve the upstream internal addon paths `addons/godot-rapier2d` and `addons/godot-rapier3d`. Use public display names `Redot Rapier Physics 2D` and `Redot Rapier Physics 3D`, with artifact slugs `redot-rapier-physics-2d` and `redot-rapier-physics-3d`, across archives, manifests, releases, catalogs, documentation, and support records.
- Use one lockstep repository version and Git tag for every package published from a release. Rapier2D can release alone until Rapier3D passes its product gate; no placeholder or preview Rapier3D artifact is created. After Rapier3D becomes public, both qualified packages advance together.
- Derive tags from the pinned upstream version using `v<upstream-version>-redot.<revision>`, beginning with `v0.35.2-redot.1`. Increment the Redot revision for downstream-only releases and reset it to `redot.1` when the upstream version changes.
- Use `../redot-porting-infrastructure` as the required repository-level build and release foundation. Reuse its language-neutral Redot identity, evidence, packaging, CI, and release contracts; replace its C++/SCons/`redot-cpp` adapter with redot-rust/Cargo.
- The first public Rapier2D package targets full applicable feature parity with the pinned upstream plugin. There is no planned post-release feature trickle: a missing upstream 2D capability blocks release unless it is technically inapplicable to Redot 26.2 or receives an explicit owner waiver.
- Windows x86-64 and Linux x86-64 are the mandatory first-release platforms. Full Rapier2D parity, packaging, export, and runtime gates must pass on both.
- A designated single-threaded deterministic Rapier2D profile must produce identical canonical replay hashes on Windows x86-64 and Linux x86-64. The separately tested parallel profile makes no cross-platform byte-equality claim.
- macOS, web, mobile, other architectures, and double precision are separate later variants, not implied by Windows/Linux success.
- Publish approved installables through both GitHub Releases and the Redot Asset Library. GitHub is the canonical release/evidence record. The Asset Library receives a separate immutable package-only commit per approved dimension and exact Redot version, created from the same staged payload and verified by installed-file path/SHA-256 equality.
- Keep installables lean: include only the dimension's runtime addon plus its README and complete legal notices. Publish examples, parity fixtures, and test projects as separate, dimension-specific GitHub companion assets under the same release tag; do not place them in Asset Library payloads.
- Publish directly to stable. Internal CI/local candidate artifacts may be used for validation, but there is no public beta, preview, or release-candidate package and no Asset Library entry before the stable GitHub release passes every required gate.
- Before stable publication, require retained real downstream confirmation for the exact candidate package on Windows x86-64 and Linux x86-64: clean install, explicit backend selection, representative runtime behavior, export, exported-release launch, and error/warning review. An explicit retained owner waiver is allowed only when no suitable downstream tester or project is available and does not waive automated gates.

Immediately before implementation freezes those inputs, re-query the official plugin `releases/latest` record and crates.io's maximum-stable metadata for both Rapier crates. The planned lock is valid only while all three stable identities still match. If the newest stable plugin does not lock the newest stable crates, stop and define an explicit dependency-upgrade compatibility gate rather than silently changing Cargo resolution.

Before implementation, either vendor the approved contract files into the Rapier repository with a recorded content inventory/hash or establish and pin a canonical infrastructure commit. Verify: the dated official freshness query still selects plugin `v0.35.2` and both Rapier crates `0.35.1`; hashes, commit identities, registry checksums, infrastructure provenance, lockfile resolution, and evidence URLs agree with `UPSTREAM_LOCK.md`; the adapted contract validates one shared toolchain/upstream lock, one release version/tag conforming to the upstream-derived Redot revision scheme, exactly one certified Redot engine/API identity, and two addon records with the exact approved display-name/slug/dimension mapping at the preserved `addons/godot-rapier2d` and `addons/godot-rapier3d` paths; the Windows/Linux-only release matrix is explicit, and every upstream 2D feature has a stable parity-ledger ID and planned acceptance signal.

### 1. P7-G0 unchanged-source 2D/3D compatibility probe

Acquire and validate Redot through the adopted porting-infrastructure bootstrap/API-dump contract. Acquire the pinned target separately from the dirty v0.35.1 research checkout. Use a Rust build adapter that externally patches crates.io `godot` to the pinned gdext fork and supplies `GDRUST_GODOT_API_JSON`; it replaces the fixture's `fetch-bindings` and SCons steps. Hash the complete tracked source payload before and after the probe. Compile unchanged Rapier source in debug and release for each minimal profile:

- Rapier top-level `single-dim2` plus dependency `godot/api-custom-json`
- Rapier top-level `single-dim3` plus dependency `godot/api-custom-json`

Do not enable Rapier's top-level `api-4-5`, `api-custom`, or any other `api-*` feature. After the minimal profiles pass, add explicit intended desktop profiles for `register-docs`, `serde-serialize`, and solver `parallel` on/off. Capture actual Cargo metadata/fingerprints rather than copying a declared feature label. Where feasible, run the same bounded upstream fixtures on Godot 4.5.2 as an oracle before Redot 26.2.

Verify: the infrastructure contract and its Rust adapter tests pass; complete source hashes remain unchanged; the graph resolves one pinned gdext source; expected entry symbols exist; staged Redot-compatible descriptors load; one real collision per dimension works; explicit Rapier selection and unchanged-default controls pass; bounded runtime fixtures and export pass. Clean-install cases cover 2D only, 3D only, both standalone addons, switch-back, missing-backend handling, and embedded single-main-extension registration. A failure stops source work and produces a minimal incompatibility report. Passing proves compatibility only, not the product feature set.

### 2. Minimal packaging adaptation

After the explicitly authorized bounded remediation passes its compatibility builds, create the smallest Redot-specific packaging delta: Redot-built binaries, compatible dimension-specific descriptors, non-reloadable policy, and additive registration metadata. Extend the infrastructure metadata from one `addon` record to two addon records that share one upstream/toolchain lock but retain separate names, entry symbols, feature profiles, manifests, and archives. Map the 2D record to `Redot Rapier Physics 2D` / `redot-rapier-physics-2d` / `addons/godot-rapier2d`; map the reserved 3D record to `Redot Rapier Physics 3D` / `redot-rapier-physics-3d` / `addons/godot-rapier3d`. Add one build-once staging output per approved dimension containing only the runtime addon plus its README and license. From that same output, create the GitHub release asset and a package-only same-repository commit suitable for the Redot Asset Library. Stage examples, parity fixtures, and test projects separately as dimension-specific GitHub companion assets. Do not refactor physics code or rewrite paths for cosmetic branding, and do not emit the 3D artifact or catalog commit before approval.

Verify: each archive and manifest uses the exact approved display name and slug, installs alone into its preserved internal path, and loads exactly one matching dimension-specific entry point; installing both approved archives together produces no path collision or duplicate class registration; default backends remain unchanged until explicitly selected; package metadata and checksums identify the correct dimension; the GitHub asset and Asset Library commit have identical installed addon paths and per-file SHA-256 values; installables exclude examples, parity fixtures, test projects, repository development files, and the other dimension; companion assets identify the same tag, Redot identity, and dimension; no 3D archive, package commit, catalog entry, or companion asset is emitted before approval.

### 3. 2D vertical slice

Prove install, editor registration, runtime selection, switch-back, one representative collision/query case, and an untouched-project control.

Verify: `Rapier2D` activates only when selected, standard behavior matches the control within documented tolerances, and switching back restores the prior backend.

### 4. Full Rapier2D parity and reliability gate

Implement and exercise the complete applicable upstream 2D surface, including standard PhysicsServer2D behavior, all provided 2D shapes and joints, collision/query/contact/callback behavior, bodies/areas/spaces, motion and character-controller paths, project settings/profiling, upstream nodes/resources and addon assets, fluids and every exposed 2D fluid effect/particle operation, and state export/import/restore. Include relevant upstream regression fixtures plus repeatable simulation hashes, stacking stability, and no-ghost collision scenarios. Test solver `parallel` on/off separately from Redot `run_on_separate_thread` on/off. Record precision, compiler, target, feature set, seed, timestep, and replay count.

Verify on both Windows x86-64 and Linux x86-64: every parity-ledger row is `Parity PASS`, `Not applicable` with reproducible technical evidence, or covered by an explicit owner-approved release waiver. Fixture-specific assertions pass; restored state matches the reference; determinism comparisons use the same protocol and report any architecture boundary rather than overclaiming. Any unclassified, untested, missing, or silently degraded applicable 2D feature blocks the public release.

### 5. 3D value/parity gate

Compare Rapier3D against the pinned Redot Jolt/default behavior for an explicitly proposed differentiating use case. Compatibility evidence from milestone 1 is necessary but not sufficient. Before 3D product implementation, name the proposed capability, freeze the Jolt and Rapier configurations and scenario, and define the observable result that Jolt cannot provide.

A documented, end-to-end rollback or deterministic replay workflow may contribute to the value case, but it cannot pass the Rapier3D gate by itself. If rollback/replay is the only material difference, record a Rapier3D no-go and preserve a backend-neutral standalone rollback plugin as a separate future candidate outside this plan.

Verify: demonstrate at least one material, testable user-facing capability unavailable in the pinned Jolt backend in addition to any rollback-only benefit; document the user benefit, remaining parity gaps, performance cost, and maintenance cost; and obtain owner approval. Compatibility, ordinary parity, an alternate implementation, benchmark equivalence, or rollback alone fails the gate. If no qualifying differentiator exists, record an explicit no-go and ship Rapier2D without a speculative 3D product surface.

### 6. Desktop determinism and performance

Define a canonical deterministic profile with pinned source, Rust/dependency/Redot/API identities, single precision, Cargo features, compiler settings, target CPU assumptions, one solver thread, Redot separate-thread execution disabled, seed, serialized initial state and inputs, fixed timestep, frame count, and stable sorted binary state encoding. Run the same replay repeatedly on Windows x86-64 and Linux x86-64 and compare checkpoint plus final hashes.

Test the normal parallel profile separately for correctness, stability, same-platform repeatability, performance, export behavior, and race-sensitive shutdown/restart scenarios. Do not label it cross-platform deterministic unless it independently earns that claim. Benchmark both profiles against Redot defaults using identical small, medium, high-body-count, and fluid workloads.

Use a release guardrail rather than an improvement mandate. Rapier2D does not have to match or beat Redot's default backend in every benchmark. Block release on crashes or hangs, physics correctness or stability failures, memory leaks or unbounded growth, workload failures hidden by aggregate results, and material unexplained frame-time or memory regressions beyond frozen thresholds. Capture baseline measurements first; before release-candidate comparison, freeze the scenario definitions, hardware and software environment, warm-up, sample counts, aggregation method, and numerical regression thresholds. Publish the raw comparison data.

Verify: the deterministic profile repeats identically on each platform and produces exact matching hashes between Windows and Linux; any unexplained divergence blocks release. Retain canonical inputs, checkpoint/final hashes, raw timings, warm-up, sample counts, compiler flags, target details, precision, hardware, and divergence diagnostics. Performance evidence proves the guardrail rather than claiming universal improvement, and the retained threshold record predates the release-candidate results.

## Failure and fallback policy

- If an unchanged future upstream fails milestone 1, identify the first incompatible revision or API surface before proposing a patch. For v0.35.2, the retained failure and owner-authorized bounded remediation are recorded in ADR-0277.
- If the official freshness check finds a newer stable plugin or Rapier crate before P7-G0, stop and refresh the lock and gate inputs. If the newest plugin and newest crates do not align, require an explicit dependency-upgrade compatibility gate rather than floating resolution.
- If v0.35.2 2D passes and optional 3D fails, keep the working 2D candidate and defer 3D rather than downgrading both.
- If Rapier3D proves compatibility and parity but no material capability beyond Redot Jolt, close the 3D product gate as no-go; do not publish a redundant backend.
- If rollback/replay is Rapier3D's only added capability, close the 3D gate as no-go and record the standalone rollback addon only as a separate future candidate.
- Lockstep versioning does not authorize or imply Rapier3D. Until the 3D gate passes, publish Rapier2D alone and fail any release that contains a placeholder or preview 3D artifact.
- Reserving the `Redot Rapier Physics 3D` name and `redot-rapier-physics-3d` slug does not authorize or imply a Rapier3D artifact.
- If an applicable upstream 2D feature cannot be matched, stop release and present the exact incompatibility and impact for an explicit owner waiver; do not silently move it to a later version.
- If the designated deterministic profile diverges within or between Windows and Linux, stop release and isolate the first divergent checkpoint before changing the claim or implementation.
- Use the proven v0.8.40 case only as a 2D single-precision bisect floor; it is not a complete fallback release.
- Do not substitute upstream API-4.7 binaries or descriptors, and do not infer Rapier compatibility from redot-rust's smoke-extension CI.
- Do not infer support for a different Redot version from technical loadability or prior evidence; create and validate a new downstream release for that exact engine/API identity.
- Do not independently rebuild or alter the Asset Library payload. A channel mismatch requires a new staged package and validated downstream release.
- Do not use a public beta or RC as a fallback for a failed stable gate. Keep the candidate unpublished, fix or explicitly waive the blocker, and rerun the required evidence before the first public release.
- If private downstream validation fails on either required platform, keep the candidate unpublished, fix the defect, and rerun the affected automated and downstream checks. Use the owner waiver only when a suitable tester or project is unavailable, never for a failed result.
- If a newer upstream stable release appears after publication, open and record its evaluation promptly but keep the current Redot release supported and pinned until the newer candidate passes the complete applicable matrix. Do not turn upstream freshness into a fixed-date or partial-release exception.
- When a new planned stable Redot release opens a routine update cycle, build a new exact-Redot downstream line and retire the prior line from routine maintenance only after the new line publishes. Continue reviewing repository issues and pull requests between cycles, but queue non-emergency accepted work for the next Redot cycle.
- When a confirmed security defect, data-loss defect, or release-blocking crash affects the current supported line, an out-of-cycle patch may proceed before the next Redot release. Freeze the smallest remediation, record the severity evidence, exclude unrelated features and routine upgrades, and rerun the full applicable matrix and normal publication flow. If the defect does not meet that threshold, queue it for the next routine Redot cycle.

## Out of scope

- A standalone rollback/replay plugin. It is a future, backend-neutral plugin candidate only if rollback is useful but insufficient to justify Rapier3D.
- A multi-version Redot compatibility claim within one plugin release.
- Rapier `main`, prerelease crates, or a floating dependency identity.
